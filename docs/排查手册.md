# 排查手册（调试期专用）

> 目的：**你遇到任何问题，把「报错信息 + 日志/诊断包」发过来，就能快速定位。**
> 本项目处于实操测试阶段，默认开启 `debug` 日志，所有关键路径都埋了稳定的「标记」。

## 一、最快的三步

**方式 A（推荐，网页点一点）**：打开 `http://<服务器IP>:8080/report`（侧边栏「**问题反馈**」）

1. 点「**一键下载诊断报告**」→ 下载 `ttdownload-report-*.zip`
2. 页面下方可看「最近失败的任务」及原因（有「复制」按钮）
3. 把 zip + 报错截图发我

**方式 B（命令行）**：

```bash
sudo ./deploy.sh --status                      # 1) 服务状态 + 健康检查
sudo ./deploy.sh --logs                        # 2) 最近 200 行日志（--logs 2000 看更多）
curl -OJ http://127.0.0.1:8080/api/system/report  # 3) 一键报告 zip
```

**方式 C（服务起不来、网页打不开时）——离线收集**：

```bash
cd ttdownload-web
sudo ./deploy.sh --collect      # 不需要服务在运行，直接把日志打包到当前目录
# → ttdownload-logs-<时间>.zip（app.log / 轮转日志 / deploy.log / app.db）
sudo ./deploy.sh --logs 500     # 同时看看最后 500 行日志
systemctl status ttdownload-web --no-pager
```

报告 zip 里有什么：

| 文件 | 内容 |
| --- | --- |
| `README.txt` | 怎么用这份报告 + 隐私说明 |
| `errors.log` | **先看这个**：只保留 WARN/ERROR 与失败相关标记的摘要 |
| `app.log` / `app.log.N` | 完整应用日志（含轮转历史，每个最多 2MB 尾部） |
| `deploy.log` | 部署/更新脚本的全部输出 |
| `diagnostics.json` | 运行环境 / 生效配置（密钥打码）/ 磁盘 / 工具版本 / 事件 |
| `system-info.json` | 磁盘、数据库、各外部工具版本 |
| `tasks.json` | 任务状态统计 + 每个失败任务的错误原因与重试次数 |
| `network.json` | 网络自检逐项结果（DNS/HTTPS/yt-dlp/YouTube/CDN/RPC） |
| `markers.json` | 日志标记说明表（`[MARK:XXX]` 的含义） |

然后把 **① 报错截图/文字 + ② 这个 zip（或 `errors.log` + `app.log`）** 发我。
诊断包里已经包含：应用与运行环境、配置（密钥已脱敏）、全部日志文件尾部、任务列表与失败原因、
外部工具可用性、磁盘状态、**网络自检结果**、以及标记说明表 —— 通常不需要你再补别的。

### 日志长什么样

```
2026-09-11T14:20:38.952Z [INFO ] [MARK:TASK_CREATE] [webvideo] 公开视频任务已入队 #12 :: {"url":"...","formatId":"137"}
2026-09-11T14:20:40.113Z [INFO ] [MARK:YTDLP_ATTEMPT] [task#12>ytdlp] 尝试方式 1/9：指定格式 :: {"bin":"yt-dlp","args":["-J",...]}
```

- `[INFO ]/[WARN ]/[ERROR]/[DEBUG]/[TRACE]`：级别

- `:: {...}`：结构化细节（argv、退出码、耗时、错误摘要；密钥自动脱敏）

## 三、标记对照表（网页「日志」页也会列出）

| 标记 | 记录什么 | 什么时候看它 |
| --- | --- | --- |
| `BOOT` | 启动/关闭、版本、运行环境 | 服务起不来、重启后确认版本 |
| `CONFIG` | 生效配置（目录/端口/并发/保留空间/工具路径） | 配置没生效、路径不对 |
| `HTTP_REQ` / `HTTP_RES` | 每个请求：方法/路径/来源/状态码/耗时 | 页面 404、接口 500、请求慢 |
| `HTTP_ERR` | HTTP 处理异常（含堆栈） | 接口报错 |
| `DISK_GATE` | 空间门控数值（free/reserve/reserved/usable/need） | 任务一直「等待中」 |
| `SCHED_TICK` | 每轮调度摘要（等待/运行/可用空间） | 队列不动、并发不符合预期 |
| `TASK_CREATE` | 任务创建（模块/URL/格式） | 任务没进队列 |
| `TASK_STATE` | 状态流转/暂停/继续/恢复 | 状态卡住 |

| `YTDLP_DONE` | 产物文件与大小、用了几种方式、总耗时 | 下载成功但没有文件 |
| `NET_CHECK` | 网络自检每一项结果 | 怀疑网络 |
| `ARIA2_RPC` | aria2 JSON-RPC 调用与错误 | aria2 任务失败 |
| `ARIA2_DAEMON` | aria2c 守护进程拉起（含完整参数） | aria2 起不来 |
| `TR_RPC` | transmission RPC（409 协商、认证、结果） | BT 报 401/409 |
| `AUTH` | 登录成功/失败、未授权访问被拒 | 打不开网页、忘记密码 |
| `ANDROID` | 安卓端每个请求（鉴权方式、UA） | App 连不上/401 |
| `PIPELINE` / `ARCHIVE` / `ENCRYPT` / `PUBLISH` | 归档→加密→发布每一步 | 卡在归档/加密、成品没出现 |
| `CLEANUP` | 上报完成后的删除 | 文件没被删掉 |
| `BT_EVICT` / `BT_CLEANUP` | 出清判定细节与目录清理（含释放字节） | BT 任务被清掉的原因 |
| `COOKIE_HARVEST` | 自动获取访客 cookies：HTTP/浏览器途径、新鲜度、自愈重试 | 抖音/TikTok 下载失败 |
| `NGINX_PROXY` | nginx 子路径反代开关：开启/关闭/回滚、完整 argv、命中的 server 文件 | 外网打不开 transmission 控制台、开关报错 |
| `SETTINGS` | 设置更新（改了哪些字段） | 设置没生效 |
| `PROC_SPAWN` / `PROC_EXIT` | **所有**外部命令的 argv/退出码/耗时/stdout+stderr 摘要 | 任何外部命令相关疑难 |
| `TOOL_STATUS` | 外部工具探测（`--version`） | 工具没装/路径错 |
| `DIAG` | 日志下载、清空、诊断包导出 | 确认导出是否成功 |
| `ERROR` | 未捕获异常/兜底错误（含堆栈） | 服务异常 |

## 四、按现象找原因（速查）

### 1. 任务一直「等待中」
```bash
grep -a 'MARK:DISK_GATE' /ttdownload/state/app.log | tail -20
```
看 `usableBytes` 与 `needBytes`：`usable = free - reserve(默认10GiB) - 运行中任务预留`。
- `usable` 为负 → 清 `xiaofeizhe_downd/` 或调小 `RESERVE_FREE_BYTES`
- `usable` 够但没启动 → 看 `moduleConcurrency`（每模块并发）与 `maxConcurrent`
- `BT` 任务还要看 `transmission` 是否可用

### 2. 在线视频失败（会员/登录/区域/CDN）

**先看清是「哪一类」失败**（这是最容易搞错的地方）：

**先看首页「网络自检」的两项**（v1.4 新增，直接给出定性结论）：

- **「出口 IP 归属」**：显示当前出口 IP、地区、运营商/机房，并判定是不是机房/海外 IP；
- **「B站（哔哩哔哩）可达性」**：分别探测首页与视频页 —— **首页 200 而视频页 412** 就是被按出口 IP 拦了。

> 真实案例：家里路由器把整网流量走了境外云主机（出口 IP 显示 `Oracle Corporation / GB / London`），
> 结果 B站视频页/接口一律 **412**、YouTube 报「确认你不是机器人」。看起来像 cookies 问题，
> 实际是**出口 IP 的归属问题** —— 换 cookies 怎么都没用。这类问题要在路由器/代理里把
> `bilibili.com`、`b23.tv`、`hdslb.com`、`bilivideo.com`、`youtube.com`、`googlevideo.com`
> 改成**国内家庭宽带直连**（或给 yt-dlp 配国内出口代理：设置 → 公开视频 → 额外参数 `--proxy ...`）。
> 抖音不受影响（它的风控只看 cookie，属实测可用的自动获取路径）。

| 报错关键字 | 真正含义 | 怎么办 |
| --- | --- | --- |
| `HTTP Error 412: Precondition Failed`（B站） | 出口是机房/海外 IP，B站拦视频页与 API（首页仍 200） | 让 B站域名走国内直连，或换国内出口代理。**不是 cookies 问题** |
| `Fresh cookies (not necessarily logged in) are needed` | 抖音/TikTok 要**新鲜访客 cookies**（不是登录） | 不用管：程序自动用 HTTP 拿 `ttwid`（约 1 秒），失败则用无头浏览器兜底；日志看 `[MARK:COOKIE_HARVEST]` |
| `Sign in to confirm you're not a bot` | 出口 IP 被 YouTube 判为机器人（**和你的账号/cookies 无关**，公开视频本来就不需要 cookies） | 等 10~30 分钟，或配代理换出口 IP；服务器 IP 被机房标记时较常见 |
| `available to this channel's members` / 年龄限制 / `Private video` | 真的要**登录 cookies** | 设置页导出一次上传（这类无法自动化） |
| 质量下拉框只有「仅音频」 | 旧版的解析 bug（分辨率为 WxH 时取错了数字），不是没有画面 | `sudo ./deploy.sh --update` 升级即可 |

```bash
grep -a 'MARK:COOKIE_HARVEST' /ttdownload/state/app.log | tail -20   # 自动获取 cookies 的过程
grep -a 'MARK:YTDLP_ATTEMPT' /ttdownload/state/app.log | tail -20    # 每次尝试用了哪套 cookies/referer
curl -u admin:密码 http://127.0.0.1:8080/api/webvideo/cookies/harvest  # 各站点 cookies 状态
```

抖音这类站点若一直失败，先确认「设置 → 公开视频（yt-dlp） → 自动获取访客 cookies」里
该站点状态是否为「已获取」；没有 chromium 也不影响抖音（它走 HTTP 途径）。
```bash
grep -a 'MARK:YTDLP' /ttdownload/state/app.log | tail -40
```
日志里有**每一种尝试的完整命令行 + stderr**。对照：
- 出现 `members-only`/`Sign in` → 需要 cookies（设置 → 公开视频）
- 出现连接超时/403 → 在「设置 → 公开视频」填 `--proxy ...`
- 首页「网络自检」面板会直接告诉你 DNS/YouTube/CDN 哪一环断了

### 3. BT 模块报 RPC 错误
```bash
grep -a 'MARK:TR_RPC' /ttdownload/state/app.log | tail -20
```
- `401` → 用户名/密码不对（脚本安装固定用户 `opengl`）
- `409` 反复 → 会话协商失败，通常也是认证或白名单问题
- 连接被拒 → `systemctl status transmission-daemon`

### 4. 安卓 App 报 401 / 拉不到清单
```bash
grep -a 'MARK:ANDROID' /ttdownload/state/app.log | tail -30
```
对比 `.env` 的 `ANDROID_TOKEN` 与 App 里填的 Token；确认端口放行（`ufw allow 8080`）。

### 4.5 安卓/网页下载速度慢（先量，别猜）

**第一步永远是测这条链路，而不是改 aria2 参数。** 用手机浏览器打开（令牌已带在地址里）：

```
http://<服务器IP>:8080/api/android/speedtest?mb=50&token=<ANDROID_TOKEN>
```

页面跑三轮，直接把 MB/s 用大字显示出来。这个数据由服务端**凭空生成、完全不读硬盘**，
所以它慢只可能是网络慢。对照参考值（树莓派 4B + 千兆网口 + 优质 SD 卡）：

| 测速结果 | 说明 | 怎么办 |
| --- | --- | --- |
| ≥ 40 MB/s | 链路很快（千兆有线/优质 5GHz） | 此时 aria2 还慢 → 查手机写入速度、aria2 参数 |
| 15 ~ 40 MB/s | 正常 5GHz | aria2 大概能跑到 70~90% |
| 8 ~ 15 MB/s | **典型 2.4GHz wifi 上限** | 换 5GHz SSID 或插网线；调 aria2 参数没有意义 |
| < 8 MB/s | wifi 信号差/干扰/距离远 | 挪位置、换信道、换 5GHz |

命令行的等价验证（在服务器本机跑，排除网络）：

```bash
# 服务端纯内存吐流能力（应 >200 MB/s）
curl -s -o /dev/null -w '%{speed_download} B/s\n' \
  "http://127.0.0.1:8080/api/android/speedtest/data?mb=100&token=$ANDROID_TOKEN"
# 磁盘裸读能力（应 ≈40 MB/s 以上）
sync; sudo dd if=/dev/mmcblk0 of=/dev/null bs=1M count=200 iflag=direct
```

另外确认服务端文件下载路由**支持 Range**（不然 aria2 只能单连接）：

```bash
curl -s -D- -o /dev/null -H 'Range: bytes=0-99' \
  "http://127.0.0.1:8080/api/android/download/1?token=$ANDROID_TOKEN" | grep -i 'content-range'
# 期望：Content-Range: bytes 0-99/<总大小>（HTTP 206）
```

### 5. 归档/加密/发布卡住
```bash
grep -a -E 'MARK:(PIPELINE|ARCHIVE|ENCRYPT|PUBLISH)' /ttdownload/state/app.log | tail -40
```
看是哪一步没有后续日志；`PROC_EXIT` 里会有 `zip`/`openssl` 的 stderr。

## 四点五、修复脚本通道（环境类问题）

代码问题走代码：我 push → 你 `sudo ./deploy.sh --update`。
**环境问题**（缺包、权限、systemd、Node 版本、目录属主…）走网页「**修复脚本**」页：

工程里自带两个可直接用的脚本（`git pull` 后位于 `deploy/scripts/`）：

| 脚本 | 用途 |
| --- | --- |
| `diagnose-env.sh` | 只读环境体检（Node/aria2/transmission/yt-dlp/DNS/磁盘/权限/服务/最近日志） |
| `fix-node20.sh` | Node 18 → 20 升级 + 重建依赖 + 重启（幂等；构建失败则不动运行中的服务） |
| `fix-ytdlp.sh` | yt-dlp 升级到最新（+deno JS 运行时 + yt-dlp-ejs），针对 `No video formats found!` / 机器人校验等 |
| `fix-ownership.sh` | 项目目录属主归位（sudo 部署后 `.git`/`node_modules`/`dist`/`public` 变 root 所有 → 普通用户无法 git pull/npm） |
| `check-ports.sh` | 端口可达性体检（本机监听 / ufw·iptables·nft / 公网探测点真实可达性）+ 建议 |
| `setup-nginx-proxy.sh` | nginx 子路径反代（`/ttdownload/` → `127.0.0.1:8080`），不动 80 根路径、可回滚 |

```
我给你 .sh（会同时告诉你是干什么的、改了什么、怎么回滚）
  ↓
你打开网页「修复脚本」→ 填维护令牌 → 打开开关
  ↓
上传脚本 → 核对预览内容 → 勾选确认 → 「上传并执行」
  ↓
页面显示执行输出与退出码 → 点「下载日志」发我
```

安全设计：

| 机制 | 说明 |
| --- | --- |
| 默认关闭 | `SCRIPT_UPLOAD_ENABLED=0`，或在页面开关里控制；不用时请关掉 |
| 维护令牌 | 写操作需要 `MAINTENANCE_TOKEN`（未设置时回退 `ANDROID_TOKEN`） |
| 执行前预览 | 上传后必须先在页面上看到脚本全文，手动确认才执行 |
| 审计与留痕 | 每个脚本与输出都落在 `/ttdownload/state/scripts/`，并打 `[MARK:SCRIPT_UPLOAD]` / `[MARK:SCRIPT_RUN]` 日志（含退出码、超时、执行方式） |
| 超时保护 | 默认 600 秒（`SCRIPT_RUN_TIMEOUT_SEC` 可调），超时按 124 结束 |
| 独立执行 | 用 `systemd-run` 起瞬时单元，脚本重启本服务也不会把自己杀掉 |
| 只收文本 | 只接受 `.sh/.bash`（或带 `#!/bin/bash`）的文本脚本，≤1MB，落盘 0700 |

> 我给你的每个脚本都会写清：**用途 / 改了什么 / 回滚方法 / 预期输出**。
> 执行前务必核对页面上的预览内容与我在聊天里说的一致。

## 四点六、两个高频外部问题（都不是代码问题）

**⓪ 先确认「yt-dlp 有一个可用的 JS 运行时」（最容易漏、症状最像网络问题）**

```bash
yt-dlp -v --simulate --no-warnings https://www.youtube.com/watch?v=jNQXAC9IVRw 2>&1 | grep -i "jsc"
# 坏：JS Challenge Providers: bun (unavailable), deno (unavailable), node (unavailable) ...
# 好：... deno, ...            （或 bun/quickjs，或 node >= 22）
deno --version || echo "没有 deno → 跑 deploy/scripts/fix-ytdlp.sh"
pip3 show yt-dlp-ejs >/dev/null && echo "yt-dlp-ejs 已装" || echo "缺 yt-dlp-ejs → 同上脚本会补"
```
缺 JS 运行时的典型报错：`No video formats found!`、`The page needs to be reloaded.`、
日志里的 `n challenge solving failed`。**这不是网络问题**，装 deno 即可（首页「网络自检」也有这一项）。

**① `ERROR: [youtube] xxx: The page needs to be reloaded.`**
yt-dlp 的已知问题（YouTube 侧改动），表现为「带 cookies 反而报这个、不带 cookies 报机器人校验」。
处置顺序：
1. 升级 yt-dlp：网页「修复脚本」页上传 `deploy/scripts/fix-ytdlp.sh` 执行
2. 程序侧已内置缓解：该错误被判定为**瞬时错误**，会在同一方式内退避重试 2 次，再换客户端；并新增了
   「跳过网页抓取（player API 直连）」档（`youtube:player_skip=webpage,configs`）
3. 仍不行就等 yt-dlp 新版，或用 `--proxy` 换出口 IP

**② `ERROR: Sign in to confirm you're not a bot`**
出口 IP 被 YouTube 判为可疑（VPN/机房 IP 很常见）。cookies 有效时基本可解；另外在「设置 → 公开视频（yt-dlp）」
的「额外参数」里加 `--proxy socks5://...` 换一个干净出口也常有效。

⚠️ **千万别短时间反复重试**：我们实测过，连续几十次 yt-dlp 请求之后，连「带 cookies + 已装 deno」也会
全部被判定为机器人（0/3 成功），等几分钟冷却后才恢复。程序侧已做缓解：
- 同一方式内遇到机器人校验/限流会**退避 30s、60s**再重试
- 换下一种方式前再等 **15s**
- 全部失败时的错误信息会明确提示「等待 10~30 分钟再重试」

cookies 是否"结构上能用"，现在网页会直接告诉你（「设置 → 公开视频（yt-dlp）」上传后自动校验：
条数 / 域名分布 / 关键字段 / 过期数量 / 告警），首页「网络自检」也新增了 `cookies` 一项。

## 四点七、权限/属主问题（`sudo ./deploy.sh` 的历史遗留）

早期版本的 `deploy.sh` 以 root 跑 `git pull` / `npm ci` / 构建，于是这些目录变成 `root:root`：

```
root:root  .git          ← 之后普通用户 git pull 报 "insufficient permission for adding an object"
root:root  node_modules  ← npm 报 EACCES
root:root  dist public   ← 构建报 TS5033: Could not write file ...
```

现在 `deploy.sh` 已经改为**以仓库属主身份**执行这些步骤；对已经出问题的机器：

```bash
# 在网页「修复脚本」页上传执行（root 权限，只改属主，不删任何文件）
deploy/scripts/fix-ownership.sh
```

脚本会 chown 到目录属主（如 `mypi`）、修好 root 的 git `safe.directory`，并验证普通用户可以 git/写文件。

## 四点八、部署能起来但外网访问不到（只开了 22/80/443）

典型环境：云服务器只开放 22/80/443，80 被 nginx 占用，应用在 8080 → 手机/外网打不开。

```bash
sudo ./deploy.sh --check-ports   # ① 体检：本机监听 + 防火墙 + 公网探测点
sudo ./deploy.sh --proxy         # ② nginx 子路径反代（默认 /ttdownload）
```

体检会分别报告：
- **本机监听**：端口是否在监听、是否只绑了 `127.0.0.1`（那样外网一定进不来）
- **本机防火墙**：`ufw` 是否放行、`iptables`/`nftables` 里的 drop/reject
- **公网可达**：借助公共探测服务（check-host.net）从外部节点实测；失败时会提示用手机 4G 复核
- **结论建议**：例如「8080 外网不可达、80 有监听 → 建议子路径反代」

反代脚本的安全性：只**新增** `location`（独立 snippet + 幂等 include），不改任何既有 location 与 80 根路径；
改动前备份、`nginx -t` 失败自动回滚；`--remove` 一键卸载。

## 四点八点五、外网打不开 transmission 控制台（9091）

现象：`http://<公网IP>:9091` 打不开；网页「BT 种子下载」页里 transmission 显示「运行中」，
但你在外面就是连不上。

原因：**9091 只监听 127.0.0.1**，而服务器只开放 22/80/443 —— 这不是故障，是本来就没有那条路。

处理：在「BT 种子下载」页最上方打开 **transmission 反向代理（远程访问 9091）** 开关，
页面随即给出 `http://<你的域名>/transmission/web/`；不想开时关掉开关，配置会被彻底删除。

```bash
sudo ./deploy.sh --bt-proxy-status     # 当前状态（enabled / 目标 / 命中的 server 文件）
sudo ./deploy.sh --bt-proxy            # 开启
sudo ./deploy.sh --bt-proxy-off        # 关闭
grep -a 'MARK:NGINX_PROXY' /ttdownload/state/app.log | tail -30   # 开关动作全过程
```

| 现象 | 原因 / 处理 |
| --- | --- |
| 开关打不开，提示「没有设置 RPC 密码」 | transmission 的 `rpc-authentication-required=false`。先在 transmission 设置里加用户名密码；确实要开可勾选「我已了解风险」强制开启 |
| 开启时报「已回滚」 | nginx 认为这段配置有问题（多半是同一个 server 块里已经有 `/transmission` 的 `location`）。报错原文就在提示里；`nginx -t` 也给出了原始报错。配置已自动还原，nginx 没有被搞挂 |
| 地址能打开但一直转圈 / 502 | transmission 没在跑，或者 9091 不在 `127.0.0.1`（改过 `rpc-bind-address`）。用 `sudo ./deploy.sh --bt-proxy-status` 看目标，或 `ss -ltnp \| grep 9091` 确认监听地址 |
| 打开后停在登录框 | 正常的：WebUI 要 transmission 的 RPC 用户名/密码（部署时设置的那组，页面「BT 反向代理」卡片里会显示用户名） |
| 提示「开关脚本不存在」 | 服务器上的代码还没更新：`sudo ./deploy.sh --update` |
| 提示「没找到监听 80 端口的 server 块」 | nginx 里没有 80 的 server 块（只有 443？）。先跑 `sudo bash deploy/scripts/nginx-proxy-toggle.sh preview` 看要手工加什么 |
| 卡片上出现红色徽章「nginx 未运行」 | nginx 装了但没在跑：配置写进去了外网也打不开，`sudo systemctl start nginx` 后再刷新 |

**关闭是真删**：`disable` 会把我们插入的 `include` 行和其它文件里的同一行都删掉，并删除
`snippets/ttdownload-proxy-transmission.conf`；改完同样跑 `nginx -t` 并 reload。
想确认删干净了：

```bash
grep -rn 'ttdownload-web managed' /etc/nginx/ || echo "已彻底移除"
ls /etc/nginx/snippets/ 2>/dev/null | grep ttdownload || echo "无残留 snippet"
```

## 四点九、登录相关

```bash
grep -E '^WEB_AUTH_(USER|PASSWORD)=' /home/*/ttdownload-web/.env    # 看当前账号密码
grep -a 'MARK:AUTH' /ttdownload/state/app.log | tail -20            # 登录成功/失败、被拒访问
```

| 现象 | 处理 |
| --- | --- |
| 打开页面只有登录框，不知道密码 | 部署时终端打印过；或 `grep WEB_AUTH_PASSWORD /home/mypi/ttdownload-web/.env` |
| 老部署升级后要求登录，但没看到密码 | `sudo ./deploy.sh --update` 会为老部署生成并打印；也可手工在 `.env` 里设 `WEB_AUTH_PASSWORD` 后 `--restart` |
| 想换账号密码 | 改 `.env` 的 `WEB_AUTH_USER` / `WEB_AUTH_PASSWORD` → `sudo ./deploy.sh --restart`（旧会话自动失效） |
| 忘了密码 / 被限流 | 改 `.env` 后重启；限流是每 IP 60 秒内失败 10 次，等 1 分钟即可 |
| 不想鉴权（不推荐） | 清空 `.env` 里的 `WEB_AUTH_PASSWORD` 后重启；启动日志会告警「任何人都能访问」 |
| curl/aria2 拉不到文件（401） | 用 `-u 账号:密码`（HTTP Basic）或 `-H "X-Auth-Token: <安卓Token>"` |

## 五、发给我什么最有用

1. **诊断报告**：网页「问题反馈」页 → 「一键下载诊断报告」，或 `curl -OJ http://127.0.0.1:8080/api/system/report`
   （若想更小：只下「错误日志摘要」`errors.log`）
2. **现象描述**：点了什么、期望什么、实际什么（越具体越好）
3. **时间点**：大概几点几分出的问题（方便在长日志里定位）
4. 如果报告太大发不出，退而求其次：
   ```bash
   # 只发失败相关
   grep -a -E 'MARK:(TASK_FAIL|TASK_RETRY|YTDLP|TR_RPC|ARIA2_RPC|HTTP_ERR|ERROR)' /ttdownload/state/app.log | tail -500 > /tmp/err.log
   # 再带上最近 500 行完整上下文
   tail -500 /ttdownload/state/app.log > /tmp/tail.log
   ```
5. 前端问题：浏览器 F12 的 Console/Network 截图（面板会用红色 toast 提示接口错误）

> 隐私说明：诊断包里的 `ANDROID_TOKEN`、RPC 密码、加密密码等都会被替换成 `***`；
> 但日志中可能包含**视频 URL / 种子名称**，如果你介意可以先自行删掉对应行。
